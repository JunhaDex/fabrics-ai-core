# 조직 공통 원칙 (SSOT)

이 문서는 fabrics company 모든 프로젝트에 적용되는 코딩/작업 원칙의 원본이다.
루트 및 각 프로젝트의 CLAUDE.md는 이 문서를 링크하고, 내용을 중복 서술하지
않는다. 원칙이 바뀌면 이 문서만 수정한다.

## 코딩 4원칙 (Karpathy 관찰 기반)

### 1. 생각 후 코딩
- 요구사항이 모호하면 임의로 가정하지 말고 질문한다.
- 해석이 여러 갈래로 갈릴 수 있으면 선택지를 제시한다.
- 더 단순한 대안이 있으면 먼저 제안한다.
- 이해되지 않는 부분이 있으면 무엇이 불명확한지 구체적으로 말하고 멈춘다.

### 2. 단순성 우선
- 요청받지 않은 기능은 추가하지 않는다.
- 1회성 코드에 추상화 계층을 만들지 않는다.
- 요청하지 않은 "유연성", "설정 가능성"을 넣지 않는다.
- 발생할 수 없는 상황에 대한 예외 처리를 넣지 않는다.
- 200줄이 50줄로 줄어들 수 있다면 줄인다.
- 기준: "시니어 엔지니어가 봤을 때 과설계인가?" → 그렇다면 단순화한다.

### 3. 외과적 수정
- 요청받은 로직만 수정한다. 인접 코드나 주석을 "개선"하지 않는다.
- 문제 없는 코드를 리팩터링하지 않는다.
- 기존 코드 스타일(들여쓰기, 네이밍, 구조)을 그대로 따른다.
- 무관한 데드 코드를 발견하면 삭제하지 말고 언급만 한다.
- 내 변경으로 인해 생긴 미사용 import/변수/함수만 제거한다.
- 기준: 변경된 모든 줄은 사용자 요청과 직접 연결되어야 한다.

### 4. 목표 중심 실행
- 작업 지시를 검증 가능한 목표로 변환한다.
  - "검증 추가" → "잘못된 입력에 대한 테스트를 작성하고 통과시킨다"
  - "버그 수정" → "버그를 재현하는 테스트를 작성하고 통과시킨다"
  - "리팩터링" → "리팩터링 전후 테스트가 모두 통과함을 확인한다"
- 여러 단계 작업은 아래 형식으로 간단히 계획을 제시한다.
  ```
  1. [단계] → 검증: [확인 방법]
  2. [단계] → 검증: [확인 방법]
  ```

## 코드 생성 규칙
- 요구된 로직에 필요한 최소한의 코드만 작성한다 (DRY 원칙 준수).
- 시간/공간 복잡도를 우선적으로 고려한다.
- 변수/함수명은 짧고 명확한 표준 네이밍을 따르며 불필요하게 장황하지 않는다.
- 요청 범위 밖의 코드는 검증하거나 리팩터링하지 않는다.
- 기존 코드의 들여쓰기, 문법, 아키텍처 패턴을 정확히 맞춘다.
- 코드부터 바로 출력한다. 대화형 서두나 이론적 설명은 생략한다.

## 응답 언어 및 톤
- 모든 응답은 한국어, 경어체로 작성한다.
- 결론/결과를 먼저 제시하고, 근거는 필요한 만큼만 짧게 덧붙인다.
- 서두 인사, 형식적 맺음말은 생략하고 결론부터 제시한다.
- 모든 정보는 신뢰할 수 있는 출처를 기준으로 사실 확인을 거쳐야 한다.
  엄격히 객관적이고 분석적인 톤을 유지한다. 불필요한 비유, 미사여구,
  감정적 형용사를 완전히 배제한다. 높은 정보 밀도와 사실적 정확성에
  집중한다.

## 작업 후 확인
- 변경 사항은 `git diff`로 검토 가능하게 남긴다.
- 30분 이상 이어지는 세션은 작업 단위로 커밋 후 `/clear`로 새 세션을 시작한다.
